# 517.鏡の原理-思想と理論および役割分担

## 鏡の原理とは

- 画面テストで考えると、まず対象という画面ではなく画面内の入力項目があげられます。入力項目は自然数Nとなりますので、つまりは人の手で｢対象を選択｣しており、それと結びつけて｢入力値｣があるのだと思います。
- つまるところ、この対象の0-1、選択の0-1、入力値の0-1および数直線上の意味のある値、これらを定義することが、テストシナリオの1フレーズに当たります。
- つまりは、定義自体の思想をテキストにまとめあげれば、今のAIならば人の代わりになってシナリオをかけるのではないか？という推測です。
- もっと詳しくいうと、画面項目というのはテストにおいてアプリオリな存在ですが、対象の選択という行動はアポステオリかつ最初の操作です。つまりは、画面項目という集合を選択し射影することで入力する値のドメインが決まります。例えば数値テキストであれば数値ドメイン=正常系、それ以外=異常系です。射影を通して決まったドメインを更に進めると(アポステオリな時間軸で時間を進めると)、次に意味のあるテストデータというドメインを決めなくてはいけません。つまりは、同値分析や境界値分析などのテスト理論とプロジェクト毎のテスト観点を組み合わせたものです。これらは列挙した正常系異常系データを採用するしないで判別できます。つまり、boolean です。これで意味のあるテストデータというドメインの要素が決まりました。
- 端的にいえば、テストシナリオはドメインとリレーションのパターンで有限的に算出できるということ、また、つまるところSQLで算出できるということです。

## 演算・運用への応用

以上のリストにおいては以下のようなことが言える。

1. もし入力値として求めるものが｢文字列｣であれば、入力桁と入力パターン(入力制限)の幅広さによって正常値として取り得る値のドメインが確定し、同時にそれ以外は異常値としてのドメインが確定する。言うならば文字列系以外は異常値であるはずで、文字列系の中でまた異常値と正常値が分けられる。例えば数値を入れてもオーケーというのは、データとしては文字列系における半角英数文字と同義であるから、この場合数値としてカウントするのではなく、半角英数文字列としてカウントすべきであり、数値のパターンが全て異常系となるようテストデータパターン自体を削除すべきである。
2. 数値でも同様で1.のドメイン区分けは同じであるから、同じことが言える。
3. ならばまずは数値を求めているか？文字列なのか？を決めればおおよそのドメインは決まることになるため、この段階でAIにデータを渡しても良いくらいであるが、ここからさらにテスト項目ごとの入力桁や入力制限をAIに渡せば、入力単位(画面やAPIの入力値や引数)全体のテストデータおよびテストケースを積み重ねで作成可能であり、それの複合型においてはすべてのパターンが演算によって算出可能である。
4. つまり、正常値以外はすべての偽りの値として演算する=鏡に映る値として演算できるためには、正常値パターンに対してTRUEを設定すればそれ以外はすべてFALSEにする、そのようなテストデータ算出器を作ることが必要であるが、その役割はAIに任せればよい。もっといえばAIにテストデータを生成させるのではなく、AIにはテスト対象のソースとこの観点表を渡して、テスト項目ごとにTRUEをつけさせるだけで、概ねよいのである。

また、うまく整理できていないが以下はこれらを応用的かつ理想的に組み立てた汎用的使用方法である。

- まず先のリストを適当な数値でパターンIDとしてタグ付けしておく。
- 次にこのパターンIDと同じレコードとなるように列Boolean で対象ならばTrueとしておけるようにする。
- さらに条件式を入れる列を複数用意しておく。これは正規表現でもよいのだが、文字列なのか？数値なのか？が分かる列ともし文字列であればどんな文字列が許容されるのか？を判別できるようにする列(ひらがな列、半角英数字列などのパターンを網羅して複数でもよい)を設けておけば、SQLでも論理演算でも演算しやすくなると考える。
- これらが終われば、おそらくは数学的な式が作成できる気がしている。ただ数学の式が複雑だと運用保守が大変であるため、ここでYAMLに変換しておく。つまり演算式は結局のところネストの深いIf文であるため、AIの認識しやすいYAMLでかつそれであればネスト表現も容易いから、運用保守も軽くなる。しかしAIに渡すそのYAMLには数学式が記載されているから、AIはYAMLと数学的演算で答えを出力する、単なるテキスト型計算機のようにコントロールできるようになる。なお、数学式はYAMLと併記しておけば人でも分かる人は分かるし、AIにとっても理解の補強となる。
- そして上記のようなデータセットがあるならば、単体テストと結合テストにおいて、APIと画面の両方で活用可能と考えている。例えばAPIの単体となればすなわちメソッドのテストやクラス単位のテストといったモジュールテストとなりやすいが、これらの引数の型=画面なら入力制限と引数の数=画面なら入力桁数によってドメインを決めればよいだけである。つまりメソッド=画面の1入力項目となる。また、画面であればラベルの存在有無や座標なども検査対象とできれば、完全なテストができると思う。つまり、ラベルというのは大体のシステムで統一されたフォーマットによって配置されるし、ほぼ常に固定値であるかイベントによって動的に数パターンの固定値が切り替わるだけであるから、APIにしろ画面にしろラベルにしろ、基本的には詳細設計書内の画面項目定義に記載の項目定義内容とその数およびインターフェース仕様とAPI詳細設計書の処理設計各項目というある程度固定フォーマットで記載されているはずのドキュメントで上記の演算がほぼ完璧に行えるのである。ほぼ完璧といったのはやはり業務ロジックのための補完インプットとしてのソースコードやテーブル定義などが時折必要となるためである。

## 人とAIとプログラムの役割分担

ここまでの話を整理して人とAIの役割を整理しようと思う。また、同時にプログラム処理という項目も並列に考えてみるとかなり楽になる。

- 人の役割
    - 鏡の原理やソースコード、画面設計書を必要な組み合わせを判断してAIに渡し、単体レベルのテスト仕様書やテストデータ、テストコードの生成をAIに指示する
    - テスト仕様書や画面設計書などのドキュメントの読み方をAIにも分かるようフォーマットを自然言語でまとめつつ説明できるようにしておく
    - 隣接テーブルを生成させるため、基本設計書や適切な画面設計書をAIに渡しつつ、隣接テーブルの生成方法をAIに分かるよう指示する
    - 生成された隣接テーブルを使ってプログラムでjoinテーブルを生成する
    - AIに結合や総合レベルのテスト仕様書を生成するよう指示する
    - AIに結合や総合レベルのテストコード仕様書を生成させる。また、仕様書のフォーマットや指示内容ないし説明内容を自然言語で整理しておく。

- AIの役割
    - 鏡の原理を使ってソースコードや画面設計書から、単体レベルのマッピングを行う
    - マッピングから単体レベルのテスト仕様書のフォーマットに従い、単体テスト仕様書を生成する
    - テスト仕様書からテストコードやテストデータを生成する
    - 基本設計書や画面設計書から、隣接テーブルを2種類生成する
    - 鏡の原理E2Eを使って基本設計書やルートが記載されているソースコードなどとプログラム処理で作成したjoinテーブルからマッピングを行う
    - マッピングから結合や総合レベルのテスト仕様書を生成する
    - テスト仕様書に沿って、どの画面メソッドやクラスメソッド、汎用メソッドなどを組み合わせるか？テストコード仕様書をフォーマットに従って生成する

- プログラム処理
    - 隣接テーブルを引数としたjoinテーブル作成プログラム
    - テストコード仕様書に沿った結合や総合用テストコード作成プログラム
    - 単体レベルのテストデータ生成APIないしプログラム
